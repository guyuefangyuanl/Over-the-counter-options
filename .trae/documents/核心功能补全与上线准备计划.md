# 全面功能梳理与补充实施方案

根据您的要求，我已对现有系统进行了深度审计。目前系统已具备基础的行情查询、交易下单和资金管理功能，但在**期权全生命周期管理**、**风险控制**、**用户触达**及**生产级运维**方面存在显著缺失。以下是详细的实施方案：

## 1. 功能清单与待补充项 (Gap Analysis)

| 模块 | 当前状态 | 缺失/待补充功能 | 优先级 |
| :--- | :--- | :--- | :--- |
| **交易核心** | ✅ 下单, 撤单, 状态流转 | **❌ 结算与行权 (Settlement)**: 到期自动结算、行权逻辑、资金划转。 | P0 |
| **风险管理** | ⚠️ 前端模拟 Greeks | **❌ 后端风控 (Risk Engine)**: 实时 Greeks 计算、敞口监控、保证金/强平逻辑。 | P0 |
| **产品中心** | ⚠️ 仅依赖行情 | **❌ 产品定义 (Product Mgmt)**: 期权合约模版管理（行权价规则、到期日规则）。 | P1 |
| **用户触达** | ❌ 无 | **❌ 通知中心 (Notifications)**: 交易状态变更通知（邮件/微信服务通知/短信）。 | P1 |

## 2. 待补充功能技术实现方案

### 2.1 结算与行权系统 (Settlement System)

**目标**: 实现期权到期日的自动结算和资金划拨。

*   **输入/输出**:
    *   输入:每日收盘数据 (Daily Close), 存续持仓 (Active Positions)。
    *   输出: 结算单 (Settlement Order), 资金变动 (Transaction), 持仓状态更新 (Expired/Exercised)。
*   **接口定义**:
    *   `POST /api/v1/trade/settlement/daily`: 触发每日结算任务 (Admin Only)。
    *   `GET /api/v1/trade/settlements`: 查询结算记录。
*   **数据库设计 (`settlements` Collection)**:
    ```json
    {
      "date": "2026-02-03",
      "position_id": "pos_123",
      "user_id": "user_456",
      "type": "exercise", // expiry, exercise
      "strike_price": 2.5,
      "settlement_price": 2.8,
      "pnl": 3000.0,
      "status": "completed"
    }
    ```
*   **实现逻辑**:
    1.  定时任务 (Celery/APScheduler) 每日收盘后运行。
    2.  遍历所有 `expire_date <= today` 且 `status=active` 的持仓。
    3.  调用 `StockService` 获取标的收盘价。
    4.  计算 PnL = `(Close - Strike) * Quantity` (Call) 或 `(Strike - Close) * Quantity` (Put)。
    5.  调用 `TradeService.deposit` (如盈利) 并更新持仓状态为 `completed`。

### 2.2 后端风控引擎 (Risk Engine)

**目标**: 实时监控平台整体敞口风险。

*   **技术方案**: 集成 `QuantLib` 或纯 Python 实现 Black-Scholes 模型。
*   **接口定义**:
    *   `GET /api/v1/risk/exposure`: 获取全平台 Delta/Gamma 敞口。
    *   `POST /api/v1/risk/check`: 下单前预风控检查 (Pre-trade check)。
*   **安全验证**:
    *   下单接口增加 `RiskService.check_limit(user_id, amount)` 钩子，超过限额自动拒绝。

### 2.3 通知中心 (Notification System)

**目标**: 交易状态变更实时触达用户。

*   **技术方案**: 异步消息队列 (Redis Queue) + 适配器模式 (支持 Email/WeChat/SMS)。
*   **接口定义**:
    *   内部调用: `NotificationService.send(user_id, template_id, data)`。
*   **实现**:
    *   在 `TradeService` 状态变更处 (下单成功、成交、结算) 触发消息投递。

## 3. 联调与压测方案

### 3.1 性能压测 (Load Testing)
使用 **Locust** 编写压测脚本，模拟真实交易场景。

*   **场景**: 1000 用户并发，每人执行 "登录 -> 查询行情 -> 下单 -> 查询持仓" 链路。
*   **指标要求**:
    *   QPS: ≥ 1000
    *   P95 响应时间: ≤ 200ms
    *   错误率: < 0.1%
*   **优化手段**:
    *   MongoDB 索引优化 (为 `user_id`, `status`, `created_at` 建立复合索引)。
    *   引入 Redis 缓存行情数据 (TTL 1s)。
    *   Gunicorn Worker 数量调整 (建议 2 * CPU + 1)。

### 3.2 稳定性测试
*   **Chaos Monkey**: 随机重启 Flask 进程，验证重连机制。
*   **长跑测试**: 持续运行 24 小时低负载脚本，观察内存泄漏。

## 4. 上线检查清单 (Launch Checklist)

### 4.1 灰度发布策略
*   **白名单机制**: 首日仅开放内部员工账号 (Role=Staff) 交易权限。
*   **流量控制**: Nginx 层配置漏桶算法 (Leaky Bucket) 限流。

### 4.2 监控与告警
*   **日志**: 接入 ELK (Elasticsearch, Logstash, Kibana) 或云日志服务。
*   **告警**:
    *   API 5xx 错误率 > 1% -> 触发 P1 告警 (短信/电话)。
    *   接口响应 > 500ms -> 触发 P2 告警 (IM 通知)。
    *   核心业务指标: 每日充值金额、成交量同环比监控。
